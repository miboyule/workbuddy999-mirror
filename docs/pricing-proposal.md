## 2. 必须先统一的底层单位

NewAPI 默认 `QuotaPerUnit=500000`，即 `ModelPrice=0.01` 会扣除 5,000 个底层额度。当前代码把 200 积分直接写成 200 个底层额度，单位相差 25,000 倍。

建议保留 NewAPI 的默认 `QuotaPerUnit`，不改全局计费单位，在 BFF 激活和展示时做转换：

```text
1 用户积分 = 25,000 NewAPI 底层额度
兑换 token.remain_quota = 套餐积分 × 25,000
页面显示积分 = NewAPI 剩余额度 ÷ 25,000
按次模型的用户积分消耗 = ModelPrice × 20
```

这样 `ModelPrice=0.01` 对应 `0.2 积分/次`，200 积分约可调用 1,000 次；NewAPI 原生日志、渠道和管理员功能仍使用原来的底层额度单位。

## 3. 三套可选方案

### A：完全复制官方

- 充值价格和积分数量完全按上表。
- 模型使用官方倍率，按截图中的基础按次价结算。
- 不额外加服务费，适合冷启动和快速积累用户。
- 风险是上游成本波动时没有缓冲，售后和支付成本需要另行承担。

### B：官方充值比例不变，模型价格增加 25%（推荐）

- 客户仍按 `20 积分/元` 购买，页面不会出现额外加价。
- 保留官方模型相对倍率，所有按次基础价乘 `1.25`，作为渠道、支付、客服和波动成本缓冲。
- 建议毛利目标为 25% 左右；实际毛利要用上游账单和失败请求退款数据复核。
- 现有套餐价格不改，已生成兑换码也不作废，只改变新请求的扣费表。

### C：官方倍率 + 分组价格

- `default` 分组使用官方价。
- `member` 分组使用官方价的 1.25 倍。
- 会员中心的兑换 token 默认进入 `member`，管理员和内部测试 token 进入 `default`。
- 优点是可以同时保留“官方体验价”和“长期会员价”；缺点是需要维护分组和迁移已有 token。

当前项目更适合先落地 B，等真实成本数据稳定后再切换 C。C 不应在没有确认分组规则前直接写入生产库。

## 4. 复购和长期留存

保持公开套餐的官方积分比例不变，把优惠放在账户权益中，避免前台价格表变得复杂：

| 触发条件 | 后续权益 |
| --- | --- |
| 首次兑换 | 正常积分、激活后一个月有效 |
| 30 天内第二次购买 | 下单自动发 3% 复购券，积分面值仍按官方比例展示 |
| 连续 3 次购买 | 5% 复购券、优先客服、保留当前模型价格 30 天 |
| 50,000 / 100,000 积分 | 专属客服和配置协助；不额外改变积分面值 |
| 会员停用后再次充值 | 恢复同一会员账户，保留历史记录和已有 API Key 管理入口 |

复购券只影响下一次订单金额，不改变兑换码积分；这样既保留官方价格锚点，也给客户留下继续在本站充值的理由。优惠券、会员等级和有效期需要在方案确认后再增加数据库字段。

## 5. 建议的上线顺序

1. 确认 A、B 或 C；若没有特别要求，建议先选 B。
2. 先做单位转换：兑换码激活、余额、密钥剩余、使用记录统一显示用户积分。
3. 写入 16 个模型的 `ModelPrice`，保留旧配置备份。
4. 用测试兑换码分别验证 200、5,000、100,000 积分的余额和扣费。
5. 再接入复购券和会员等级，不改已有兑换码的前缀、长度和激活规则。
